# 项目决策记录（ADR）

> 记录"为什么这么定"，避免几个月后重新纠结或跑偏。新决策往下追加，旧决策不删；推翻时写"被 Dxx 取代"。

## D1 产品定位：agent 的宿主，不是又一个 agent

CyberBadge 提供**运行环境 + 多 agent 切换 + 借屏 UI**，不自研通用 agent。自带一个最小兜底（builtin：对话 + 工具 + 技能），够用即可，不追功能。
原因：通用 agent 能力（技能、多会话、记忆、工具生态）已有人做得更好；我们的差异在硬件形态、随身入口、多 agent 统一调度。

## D2 胸牌只当遥控器，Hub 跑在服务器/桌面

实测（2026-11-21，服务器 3.6GB）：DSH web 进程 RSS 约 587MB + billion-context 约 442MB ≈ 1.0GB；Hermes 容器 727MB；两者同时约 1.7–2.2GB，3.6GB 里靠 swap 才挤下。
结论修正：**4GB 板子单独跑一个 DSH 是可能的**（约 1GB），但"DSH + Hermes + Chromium + LibreOffice 并发"不行；8GB 才是舒适线。ARM 的真正风险不在内存，而在依赖是否有 arm64 预编译（Node 官方有，个别原生模块待验证）。
因此：胸牌负责"显示 + 输入 + 常驻联网"，重活放服务器/台式机；v2 本地多 agent 建议 8GB 起，16GB 更稳。

## D3 借屏优先，不自研手机 OS

UI 用 PWA，跑在用户手机上；胸牌不开显示服务。M1（自带屏）也只是 Chromium kiosk 复用同一套 PWA，不做独立 OS。

## D4 先在 x86 上开发，再移植 ARM

业务层保持系统无关（Python 标准库 + pip），硬件相关收进 `platform/` 适配层（空实现起步）。
必须真机早测的只有：功耗/掉电、散热降频、Wi-Fi 稳定性、性能上限。
纪律：不写死路径（走 `AGENT_WORKDIR` 等环境变量）、不直接调 `iw`/`nmcli`、依赖分 `requirements.txt` + `bootstrap.sh` 两层。

## D5 M0 硬件：8G 无屏 Wi-Fi 移动服务器

M0 = 8GB 内存、无屏（手机浏览器当屏）、Wi-Fi、外接充电宝，BOM 约 440–530 元。
暂不升 RK3588：等 ACP 验证通过、且"本地多 agent"成为刚需再换；换的话 8GB 是底线、16GB 才舒服，电池要 20,000mAh 起。

## D6 权限分级，而不是"最高权限"

"随时用最高权限调动设备"不可接受。采用 L0 只读 / L1 低危 / L2 高危（二次确认+审计）/ L3 根（默认不开放）。
原则：可审计、可撤销、丢失可吊销。

## D7 内容边界

不生成对未成年人形象（官方设定为儿童体型）的性化内容，包括"受缚/捆绑"题材；不调用训练数据明显成人向的 LoRA。可做正常向立绘、非儿童体型角色的轻度题材。

## D8 保留 LibreOffice（带资源闸门）

排版保真只能用 LibreOffice；python-docx 只做内容级编辑。
实现约束：单并发 flock、内存低于 700MB 拒绝启动、120s 超时杀进程组、独立 profile 目录。

## D9 安全优先于功能（已落地第一步）

当前状态（无鉴权、局域网可访问）不可长期运行。已实现：令牌鉴权（header/query/cookie）、按 IP+类别的限流、审计日志、WS 令牌校验。优先级：Token 鉴权 → 仅监听 Tailscale/局域网白名单 → 限流 → HTTPS。
反对为"隐藏设备列表"启用 pf 等整机级规则（风险大于收益）。

## D11 现阶段明确不做

- 不自研手机 OS / ROM；
- 不在胸牌上跑本地大模型；
- 不做通用多 agent 运行时（交给 DSH/Hermes）；
- 不为"能接 100 个 agent"做功能；
- 不追新硬件，除非软件已验证需要。
